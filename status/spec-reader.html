§1Problem statement

AI agents (Claude in Cowork, Claude Code, a chat's code sandbox) and downstream tools such as literary-critic need to read and change Word documents quickly, precisely and safely, while the writer — a non-technical person — keeps full control: every content change must be visible and rejectable in any Word version, and work must never be lost. Today this is done with computer use, ad-hoc scripts or docx-fixer, which only handles Spanish-novel typography and rewrites whole XML parts. Generic libraries do not fit: python-docx cannot write tracked changes, comment replies or the resolved state, and naive xml.etree serialisation silently drops namespace declarations listed in mc:Ignorable, which makes Word report the file as corrupt. This spec covers the first deliverable of doc-control: a deterministic, stdlib-only Python core with a file engine that edits a closed .docx, exposed through a JSON CLI, with stable addresses and anchors, all-or-nothing tracked-change batches, styles and templates, recipes, and a safety layer (lock and change detection, backups, verification, automatic restore, permanent undo log). The API is designed so that a live engine (Word on Windows via COM, later Mac) and an MCP front door can be added without breaking it; those are separate specs.

Success criteria (measurable) — each seeds a task Gate in the plan:

Safety and correctness - [ ] unintended_changes == 0 — over the test corpus, after every operation, everything outside the operation's declared footprint is identical to the input. The footprint is the targeted paragraphs in word/document.xml plus a fixed per-operation allowlist of supporting parts; every other zip member is byte-identical, and inside allowed parts only the entries the operation owns may change:

Operation family Supporting parts that may change
Text, paragraph, direct-formatting and revision accept/reject edits none beyond the targeted paragraphs
Comments (add, reply, resolve) word/comments.xml, commentsExtended.xml, commentsIds.xml, commentsExtensible.xml, people.xml (only the entries for the touched comments/authors); [Content_Types].xml and word/_rels/document.xml.rels only when a comment part is created
Styles and style sets (create, update, rename, merge, install) word/styles.xml (only the touched style entries; for rename/merge also the style references in affected paragraphs); word/stylesWithEffects.xml when present; [Content_Types].xml and document.xml.rels only when styles.xml is created
Batches the union of their operations' footprints

The verifier computes the expected footprint before writing and fails (then auto-restores) on any change outside it. - [ ] untouched_parts_byte_identical_ratio == 1.0 - [ ] xml_parse_errors == 0 and ooxml_validator_errors_introduced == 0 (the .NET OOXML validator and a LibreOffice round trip run in CI; errors already present in the input do not count). - [ ] content_edits_without_revision_markup == 0 when tracked mode is on (the default). - [ ] text_after_reject_all == original_text — rejecting every revision the tool wrote restores the input text exactly. - [ ] partial_writes_on_failure == 0 — fault injection at every stage of a batch leaves the original file unchanged (byte-identical) and a restorable backup. - [ ] writes_with_word_lock_present == 0 and writes_after_external_change_without_force == 0 (~$ lock file and on-disk hash/mtime checked before every write). - [ ] edits_applied_to_wrong_paragraph == 0 — fuzz test: random structural edits between read and write always yield stale, never a misplaced edit. - [ ] backup_before_write_ratio == 1.0; every failed verification restores automatically (auto_restore_success_ratio == 1.0). - [ ] undo_roundtrip_mismatches == 0 — undoing any logged operation returns the document text and paragraph properties to their prior state; restore brings back any logged deleted paragraph as a tracked insertion. - [ ] Recipes: applied_without_dry_run_or_batch == 0; user (declarative) recipes cannot read or write anything except through batch proposals (user_recipe_capabilities_outside_batch == 0, checked by test).

Performance (reference machine: GitHub-hosted ubuntu-latest, CPython 3.11, synthetic 100k-word novel) - [ ] rename_100k_words_p95_s <= 5 (find + atomic batch + write + verify). - [ ] find_100k_words_p95_ms <= 1000; outline_100k_words_p95_ms <= 1000. - [ ] open_and_index_100k_words_p95_s <= 2.

LLM ergonomics - [ ] default_response_tokens_p95 <= 2000 (estimated as bytes/4) and every list is capped with a next cursor. - [ ] operations_without_json_schema == 0; help --json and capabilities list every operation. - [ ] responses_without_api_version == 0; every error carries a code from the published list and a one-line hint (errors_without_code_or_hint == 0). - [ ] interactive_prompts == 0 (no command ever waits for stdin unless input is piped explicitly).

Portability and dependencies - [ ] third_party_imports_in_package == 0 (stdlib only). - [ ] Test suite green on Python 3.11 and 3.13 × Linux and Windows in CI; the file engine runs in a Python 3.11 sandbox with no network (smoke test in CI with network disabled).

Anchors and segmentation - [ ] reanchor_success_ratio >= 0.98 on an edit corpus where up to 10% of characters around the anchor changed; wrong_anchor_matches == 0 (ambiguous or weak matches return ambiguous / not_found, never a guess). - [ ] Spanish sentence segmentation boundary_f1 >= 0.98 on a gold set of at least 500 sentences covering abbreviations, ¿¡, «», ellipses and raya dialogue.

literary-critic indexing support (D-18) - [ ] para.get and outline report empty, blank_before, heading level, style, centred and page break before (layout_fact_mismatches == 0 on the corpus). - [ ] A normalised-text view (NFC, soft hyphens and zero-width characters removed, whitespace collapsed) with a two-way offset map to visible text (offset_map_roundtrip_mismatches == 0). - [ ] Structure detection returns stable chapter and scene ids, the signal behind each detection, accepts fingerprint-keyed overrides and per-profile settings such as minimum chapter words (structure_override_failures == 0). - [ ] anchor.resolve with mode: "exact" never returns a fuzzy match and every response names its match kind (exact_mode_fuzzy_matches == 0). - [ ] diff aligns two versions of a document paragraph by paragraph (unchanged, modified, moved, split, merged) and returns a cross-version address map (diff_alignment_errors == 0 on corpus pairs with known edits). - [ ] locate returns, per paragraph, chapter, scene, estimated page and the shortest unique first-and-last-words phrase (locators_not_unique == 0).

Parity and coverage - [ ] docx-fixer parity (D-17): every generally useful docx-fixer rule ships as a bundled recipe and its round-trip cases pass (docx_fixer_general_cases_failing == 0); every owner-specific rule (house style ids, house template, the owner's author-note patterns) is expressible as a declarative user recipe or user style set, shown by tests on synthetic documents (owner_rules_not_expressible == 0). The owner's actual user recipes and style sets live on the owner's side, never in the repo. - [ ] Bundled recipes beyond docx-fixer cover common needs (whitespace and empty-paragraph cleanup, quotes and dashes per language, ellipsis, fake centring and fake tabs, leftover revisions/comments/highlights/hidden text, direct formatting to style, language tags, scene-break normalisation, heading hygiene); the final list is fixed in design, each with tests (bundled_recipes_without_tests == 0). - [ ] Private corpus: real documents are used only from a directory outside the repo given by an environment variable; tests skip when it is absent; no file name, title, path or excerpt of a private document is ever committed or printed in CI logs (private_corpus_identifiers_in_repo == 0, checked by the hygiene gate against a local denylist that itself stays outside the repo). - [ ] Styles: installing an exported style set reproduces the style definitions (style_definition_diffs_after_roundtrip == 0); exported .dotx passes the validator; applying a style is recorded as a tracked formatting change. - [ ] line_coverage >= 0.90 for the package. - [ ] Judged, not measured: one manual check on real Word (Windows, Word 2016 or later, and M365 when available) that tool output opens without a repair prompt and that every revision and comment can be accepted, rejected, replied to and resolved. Recorded as evidence with screenshots. Left unmeasured for the first release by owner decision (2026-10-12); done when a Windows machine is available.

§3Options

✎Your noteSPEC §3

▸Option A: Extend docx-fixer's engine (Conservative)

  • Description: Rename and generalise docx-fixer: keep its ElementTree parse-and-reserialise model (with its mc:Ignorable pruning workaround), its text model with per-character offsets, and add tracked changes, comments, addresses, batches and a JSON CLI on top.
  • Scope: Port of package.py, xmlns.py, document.py, findings.py, rules and template code; new CLI and safety layer.
  • Effort: Medium
  • Tradeoffs: + reuses tested code and known OOXML traps; + fastest to a first release. − Re-serialising whole parts changes bytes outside the edited range (attribute order, prefixes, declarations), so unintended_changes == 0 and byte-identity can only be approximated; − the pruning workaround hides the namespace problem instead of avoiding it; − its rule/finding model is novel-specific.
  • Compatibility: New package; no existing API to keep.
✎Your noteSPEC › Option A: Extend docx-fixer's engine (Conservative)

▸Option B: New core with a splice writer (Recommended)

  • Description: A new stdlib-only package. Parts are read with ElementTree for indexing, but writing never re-serialises a whole part: each changed paragraph (w:p) is serialised on its own and spliced into the original part bytes at its recorded byte span, keeping the original root start tag and every untouched byte. Untouched zip members are copied with their original ZipInfo and order. On top: position+fingerprint addresses (D-9), quote anchors with re-anchoring, a typed operation model where every operation has a JSON Schema (D-8), all-or-nothing batches with dry run and preview diff, tracked changes by default with configurable author (D-10), the safety layer (D-13, D-15), styles and JSON style sets with .dotx export/import (D-16), and recipes in three layers (D-11). docx-fixer's code is used as a reference and its tests as a corpus, not as a base.
  • Scope: New doc_control/ package (core, file engine, CLI, recipes, styles), test corpus generator, CI matrix.
  • Effort: Large
  • Tradeoffs: + byte-identity outside the edited paragraphs is achievable and testable; + avoids the namespace trap by construction; + engine-neutral operation model ready for the live engine; − more upfront work; − splicing needs exact byte spans per paragraph (a small stdlib tokenizer or position tracking), which must be fuzz-tested; − edits that touch part-level structures (comments, styles, numbering, settings) still need careful per-part writers.
  • Compatibility: New package; API versioned from the first release (D-12).
✎Your noteSPEC › Option B: New core with a splice writer (Recommended)

▸Option C: Full DOM with lxml

  • Description: Use lxml (or python-docx plus lxml) for a full, namespace-faithful DOM and re-serialise touched parts.
  • Scope: Same features as B, built on lxml.
  • Effort: Medium
  • Tradeoffs: + mature XML handling, namespaces preserved; + simpler edits on complex structures. − Third-party C extension: breaks the stdlib-only requirement and the chat sandbox target (D-7); − complicates Windows/Mac packaging; − whole-part re-serialisation still changes bytes outside the edit.
  • Compatibility: New package; conflicts with D-7's portability goal.
✎Your noteSPEC › Option C: Full DOM with lxml

§4Recommendation

Recommended option: Option B — it is the only option that can meet unintended_changes == 0 with byte-identical untouched content, keeps the package stdlib-only for the chat sandbox (D-7), and gives the live engine an engine-neutral contract. docx-fixer remains the source of OOXML lessons, rules and test cases.

Scope of v1 (from the decisions log) - Read: outline, stats, styles and fonts in use, paragraph with formatting, estimated page of a paragraph (marked estimated), find (literal, regex, case- and accent-insensitive, whole word; capped output with cursors), comments with replies and resolved state, tracked revisions with authors, history search by quote; for literary-critic (D-18): layout facts, normalised-text view with offset map, structure detection with ids/signals/overrides, exact-only anchors, paragraph diff between versions, unique-phrase locators. - Write primitives: replace a range's text, insert/delete paragraphs, move a range of paragraphs (written as a tracked deletion plus a tracked insertion in v1), apply a style or direct formatting, alignment and indentation, add/reply/resolve comments, accept/reject revisions, rename a term (word boundaries, case options) as one atomic batch, restore from the undo log. - Addresses p142#a7b2 with stale errors and an old→new address map after structural edits; quote+context anchors with re-anchoring; segmentation into paragraphs, Spanish-aware sentences, dialogue lines, scene breaks, chapters (per-profile settings). - Batches all-or-nothing with dry run and preview diff; tracked changes by default; author default "Claude" plus per-call tag. - Safety: lock and on-disk change detection, backup before every write and on every open, verification, automatic restore, permanent append-only undo log, retention 20 backups / 30 days, .doc-control/ next to the document with an app-data option. The retention rule prunes full backups only, never undo-log entries. Undo history is removed only by an explicit history purge (whole log or before a date; for privacy), which itself is confirmed with a dry run and logged as a tombstone. In app-data mode, history is keyed by a document id stored in the log; history whose document no longer exists is never deleted automatically and is listed by history orphans so the user can restore or purge it. - Styles: list/read/create/update/apply/rename/merge; JSON style sets as source of truth; .dotx export/import; style sets stored on the user's side. - Recipes: bundled (Python allowed, tested here; only generally useful recipes, including the general docx-fixer rules and other common fixes; owner-specific rules become user recipes, D-17) and user (declarative only, stored on the user's side, created by the agent on the fly or saved); every recipe yields a batch proposal. - CLI with JSON I/O, help --json, capabilities, API version in every response, stable error codes with hints. - Out of scope (later specs): live engine (Windows first, then Mac), MCP server and .mcpb/plugin packaging, Skill packaging for the chat sandbox, Google Docs/.odt, contract test suite (after literary-critic integrates), visual review page.

Immediate next action: owner reviews this spec through the annotated reader; on approval, run design to write contracts (operation schemas, error codes, address and anchor formats, .doc-control/ layout), the risk register and the task split, starting with the splice writer and its fuzz tests, since every other gate depends on it.

References in the repo are updated after the rename.

Writer notes in the text (owner request, 2026-10-12): a writer may leave instructions inside the manuscript, e.g. a paragraph ========== Move this after chapter X. Detecting and interpreting them is downstream work (literary-critic or the agent); the core only has to make applying them possible with primitives: find (regex) locates the markers, chapter detection resolves "chapter X", and one batch moves the target range, deletes the marker paragraph, and optionally adds a comment, all as tracked changes. A contract example in design covers this scenario end to end.

▸API contracts

CLI invocation — doc-control <op> [--json '<request>' | < request.json]

  • Auth: none (local process). No network access, ever.
  • Request: one JSON object; doc is a path to a .docx. Read operations may pass limit and cursor.
  • Response envelope (success): json {"api": "1.0", "ok": true, "op": "find", "doc": {"path": "Novela.docx", "sha256": "9f2c…", "paragraphs": 4120}, "result": {"matches": [{"at": "p142#a7b2:10-15", "text": "María", "context": "…dijo María, y…"}]}, "warnings": [], "next": "c:find:2f1e"}
  • Response envelope (error): exit code 1 (2 for usage errors), same envelope with ok: false: json {"api": "1.0", "ok": false, "op": "batch", "error": {"code": "STALE_ADDRESS", "message": "p142#a7b2 no longer matches the document", "hint": "Re-read the paragraph (para.get) or resolve its anchor, then retry.", "details": {"at": "p142#a7b2", "found": "p142#c01d"}}}
  • Errors (stable codes, each with a one-line hint): DOC_NOT_FOUND, NOT_A_DOCX, DOC_LOCKED (Word ~$ lock file present), DOC_CHANGED_ON_DISK (sha256 differs from expect.sha256), SCHEMA_INVALID, ADDRESS_INVALID, STALE_ADDRESS, ANCHOR_NOT_FOUND, ANCHOR_AMBIGUOUS, UNSUPPORTED_CONTENT (range crosses a field, hyperlink, content control or other structure v1 does not edit), BATCH_CONFLICT (overlapping operations), VERIFY_FAILED_RESTORED (verification failed; original restored), STYLE_NOT_FOUND, STYLE_CONFLICT, RECIPE_INVALID, HISTORY_NOT_FOUND, INTERNAL.
  • Backwards compatible: n/a (first version).

Addresses and ranges

  • Paragraph: p<n>#<fp> — n is the 1-based index over the main story's paragraphs in document order (table-cell paragraphs included); fp is the first 4 hex digits of BLAKE2s over the paragraph's visible text (inserted text included, deleted text excluded), NFC-normalised.
  • Range inside a paragraph: p142#a7b2:10-15 (character offsets, end exclusive). Range across paragraphs: p142#a7b2:10..p144#0c9e:3. Sentence: p142#a7b2.s3.
  • Every write re-computes fp for each address it touches; any mismatch fails the whole batch with STALE_ADDRESS. Structural edits return address_map (old → new) for every paragraph whose index changed.
  • Headers, footers, footnotes and endnotes are listed read-only in v1 (h1:p3, fn12:p1 style addresses reserved).

Anchors

{"exact": "María cerró la puerta", "prefix": "Al final, ", "suffix": " sin mirar atrás.", "hint": "p142"}

anchor.resolve returns {"at": "p151#9d0e:4-25", "score": 0.97} or ANCHOR_AMBIGUOUS (with up to 5 candidates and scores) or ANCHOR_NOT_FOUND. Matching is exact first, then fuzzy within candidate paragraphs found by fingerprint and word overlap; score = 0.5·quote + 0.2·prefix + 0.2·suffix + 0.1·position; minimum accepted score 0.80; ties within 0.02 are ambiguous.

Operations (v1)

Read: capabilities, help, info, outline, stats, para.get (includes empty, blank_before, heading_level, style, centred, page_break_before), find, styles.list, style.get, comments.list, revisions.list, page.estimate (always "estimated": true), segment (sentences, dialogue lines, scene breaks, chapters; stable ids, detection signals, overrides and profile parameters), text.normalized (with offset_map), diff (two documents → alignment and cross-version address_map), locate (chapter, scene, estimated page, unique phrase), anchor.create, anchor.resolve (mode: best default or exact; response includes match: exact or fuzzy), history.list, history.search, recipe.list, styleset.export.

Write (each runs as a batch): batch, restore, undo, history.purge, recipe.run (returns a proposal batch; applying it is a separate batch call), styleset.install, styleset.import-dotx, styleset.export-dotx (writes a new .dotx, never touches the document).

Batch operations: text.replace, para.insert, para.delete, para.move, style.apply, format.apply (run: bold, italic, underline, small caps, font, size; paragraph: alignment, indents, spacing), comment.add, comment.reply, comment.resolve, revision.accept, revision.reject, term.rename (expands into text.replace operations; options: whole word, case-sensitive, preserve case, inflection list), style.create, style.update, style.rename, style.merge.
